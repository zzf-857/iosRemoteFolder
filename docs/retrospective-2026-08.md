# iosRemoteFolder 项目复盘

- 日期：2026-08-11
- 结论：暂停开发，保存为学习与技术实验快照
- 证据边界：工作区所有者在开发过程中注意到 ES 文件浏览器等成熟产品；本复盘没有独立核验该竞品的全部功能、质量或商业表现

## 一句话结论

这次浪费的主要原因不是写代码慢，而是没有在大量写代码前证明“为什么值得做”；多 Agent 又把尚未验证的方向推进得更快。

## 发生了什么

项目从 Alist 媒体播放逐步扩展为统一资源查看器，范围覆盖多来源连接、六类查看器、缓存、离线、位置恢复、搜索和大媒体 Range 串流。工程上形成了不少可复用资产，但产品验证一直落后于实现：我们先处理协议、架构和 UI，再补问用户为什么不用成熟文件管理器。

当工作区所有者重新看到成熟竞品后，项目缺少清晰切换理由的问题变得无法忽视。继续开发能提高功能数量，却不能证明它值得成为一个独立产品，因此项目暂停。

## 核心失误

### 1. 把可实现性当成值得实现

“SwiftUI、WebDAV、AVFoundation 能否做出来”是工程问题；“目标用户是否愿意换产品”是产品问题。前者的肯定答案不能替代后者。

### 2. 竞品扫描发生得太晚

竞品调研不是为了寻找“从未有人做过”的空白，而是为了确认现有替代方案、用户抱怨、切换成本和仍未解决的场景。这个项目直到投入大量实现后，才重新审视成熟替代品。

### 3. 范围扩张早于差异化

从播放器扩张到统一查看器后，功能矩阵迅速变大，但一句话差异化仍不成立。功能越全，越容易落入与成熟综合产品正面对比，同时增加测试、协议兼容、缓存和生命周期成本。

### 4. 用工程进展代替产品证据

测试通过、架构整洁、真机能启动都很重要，但它们只能说明实现质量，不能说明需求强度、留存或付费意愿。里程碑长期围绕提交和测试数量组织，缺少用户行为证据。

### 5. 多 Agent 放大了方向

并行 Agent 很适合边界清晰且方向已验证的工程任务。方向未验证时，它会同时扩张代码、测试和文档，增加沉没成本与协调成本。并行度是吞吐量控制，不是方向判断机制。

### 6. 没有预先定义停止条件

项目没有明确规定“什么证据拿不到就暂停”。于是每个局部问题都自然导向下一轮修复，而不是触发一次产品层复核。

## 保留下来的价值

暂停不等于所有产出无效。以下资产仍可用于未来范围更窄、价值更明确的项目：

- 统一资源身份、revision、typed metadata 和能力模型；
- WebDAV/Alist 认证、DAV XML、重定向脱敏和 Range 响应校验经验；
- 受预算、可取消的内容会话；
- `AVAssetResourceLoader` 与远端区间读取桥接实验；
- SwiftData 配置、索引、最近记录、阅读位置和缓存迁移经验；
- 对真实服务端行为与受控 fixture 证据边界的记录方式。

这些资产只有在新产品假设通过验证后才值得复用，不应反过来成为“因为已经写了，所以继续做”的理由。

## 以后项目的六道立项门

### 1. 竞品扫描

先列出直接竞品、相邻替代、系统自带能力和用户当前的手工方案。至少回答它们已经解决什么、用户为什么仍抱怨、切换成本是什么。

### 2. 用户痛点证据

至少获得若干条来自目标用户的具体任务、频率、当前 workaround 和失败成本。一次灵感、单个帖子或开发者自己的偏好只能形成假设，不能形成确认。

### 3. 一句话差异化

必须能用一句话说明“为谁、在什么场景、比现有方案好在哪里”。如果差异只是“更全、更漂亮、我也能做”，不进入完整开发。

### 4. 最小风险验证

先验证最可能让项目失败的假设。产品风险用访谈、落地页、可点击原型或人工服务验证；协议和性能风险才用代码 POC。不要用完整 App 同时验证所有风险。

### 5. 明确停止条件

在开始前写明时间盒、最低证据和终止阈值。例如：两周内找不到 5 位高频目标用户，或没有 3 位愿意迁移真实数据，就暂停而不是增加功能。

### 6. 通过后再扩大实现与并行度

单线程完成最小纵向切片并确认价值后，再按清晰文件和接口边界启用多个 Agent。每增加一组并行任务，都要能追溯到同一个已验证产品目标。

## 新的执行顺序

```text
问题假设 -> 竞品与替代扫描 -> 用户证据 -> 差异化 -> 最小风险验证
        -> 停止/继续决定 -> 单一纵向切片 -> 工程质量门 -> 并行扩张
```

每个阶段都要区分三种证据：用户说了什么、真实行为证明了什么、工程 fixture 证明了什么。三者不能相互替代。

## 何时可以恢复本项目

只有同时满足以下条件才考虑恢复，而不是因为已有代码较多：

- 找到明确、可重复出现且成熟产品未很好解决的 iOS 远端资源场景；
- 至少有一组目标用户愿意迁移真实来源或持续使用原型；
- 差异化可以缩成一个小而完整的核心任务；
- 先通过真实 iPhone 上的关键协议/性能 POC；
- D-050、D-052 的数据一致性和传输风险被重新拆成独立验收门。

在此之前，仓库只作为实验快照维护，不继续功能扩张。
